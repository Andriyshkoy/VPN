# VPN node-agent

Закрытый API управления двумя транспортами на одном VPN-узле:

| service_id | Транспорт на текущем NL |
| --- | --- |
| `hysteria` | Hysteria2 + Salamander, UDP1935 |
| `vless-reality` | VLESS + REALITY + Vision, TCP9443 |

Это технический агент узла. Пользователи продукта, баланс, платежи, тарифы
и подписки остаются в центральном Hub. Локальная SQLite хранит идентичность
доступов, desired/observed state и журнал идемпотентных операций.

В переходной схеме агент использует существующие Marzban и Hysteria/Blitz,
сохраняя прежние ключи. Он управляет только созданными им аккаунтами с
сохранённым access ID, техническим namespace и marker. Прежние пилотные
и пользовательские аккаунты не принимаются под управление автоматически.

[Предложение по архитектуре и репозиториям](docs/architecture-proposal.md).

## API v1

| Метод и путь | Назначение |
| --- | --- |
| `GET /healthz` | Жив ли процесс агента |
| `GET /readyz` | Готовность локальных backend |
| `GET /openapi.json` | Версионированный контракт OpenAPI |
| `GET /v1/services`, `GET /v1/nodes` | Каталог транспортов и локальный узел |
| `POST /v1/accesses` | Создание доступа |
| `GET /v1/accesses`, `GET /v1/accesses/{id}` | Реестр и наблюдаемое состояние |
| `PATCH /v1/accesses/{id}` | Изменение срока, квоты или внешней ссылки владельца |
| `POST /v1/accesses/{id}/suspend` | Приостановка |
| `POST /v1/accesses/{id}/resume` | Возобновление без замены ключа |
| `DELETE /v1/accesses/{id}` | Отзыв с сохранением локальной tombstone |
| `GET /v1/accesses/{id}/profile` | Явный экспорт секретной ссылки |
| `GET /v1/accesses/{id}/usage` | Учтённый расход и ограничения точности |

Кроме liveness, запросы требуют Bearer token. Разрешения: `access:read`,
`access:write`, `profiles:read`. Последнее отдельно защищает экспорт ключа.
Это машинные/operator credentials, а не токены конечных клиентов бота.
`owner_ref` — внешний идентификатор, не механизм tenant-авторизации.

Мутации требуют `Idempotency-Key` (8–128 допустимых символов). Ключ связан
с principal и каноническими методом/путём/телом. Совпадающий повтор возвращает
тот же результат; другое тело с прежним ключом —409. После неоднозначного
сбоя backend повторяется прежняя операция с прежним backend username,
а не выдаётся новая идентичность. Технический outcome не считается
подтверждением работы клиентского трафика.

Основные коды:400 отсутствующий idempotency key,401 нет авторизации,
403 нет scope,409 конфликт,422 недопустимые параметры,503 backend недоступен.
Ответы имеют request ID и `Cache-Control: no-store`. Секретные профили
не входят в списки, usage, журнал локальных операций и сообщения ошибок.
Ограничение входного тела16 КиБ действует и для chunked запросов.

## Сроки и квоты

- `traffic_limit_bytes=0` означает безлимит; положительная квота учитывает
  upload+download. Нулевые квота/дни проверены на действующем Hysteria auth.
- VLESS принимает `expires_at` с часовым поясом UTC/offset и точностью секунды.
  Отсутствующий срок — без ограничения.
- Hysteria принимает `activation_days` (1–3660) с дневной точностью от первого
  подключения. `null` — без срока. `expires_at` для неё отклоняется с422;
  скрытого округления в дни нет. Создание/изменение/возобновление не вызывает
  положительный auth и не активирует оплаченный срок заранее.
- Hysteria `max_sessions=null` (также отсутствие поля) — без ограничения,
  `1..128` — максимум одновременно аутентифицированных QUIC-подключений на
  credential в одном экземпляре сервера (официальное приложение создаёт один
  экземпляр на процесс). Это не счётчик TCP/UDP-потоков и не
  идентификация устройства или IP. Одно подключение может нести много потоков.
  Для лимита bridge перед записью в Mongo требует `/capabilities` одновременно
  у patched Hysteria engine и фактического HTTP auth callback при активном
  `auth.type=http/https`. Старый engine
  или callback сохраняет обычную readiness и unlimited-доступ, но создание/
  изменение ограниченного доступа вернёт503 `hysteria_max_sessions_unsupported`
  без изменения Mongo. `GET /v1/services` показывает проверенную capability.
  VLESS с ненулевым `max_sessions` отклоняется с422. При уменьшении лимита
  bridge сначала проверяет native `close_by_auth_id`, сохраняет pending marker
  вместе с политикой и вызывает `/close`. До подтверждения новые auth запрещены;
  при ошибке503 повтор с тем же idempotency key завершает close. Увеличение/
  снятие лимита и изменение иных параметров без tightening не обрывает сессии.
- У Hysteria отметка активации появляется после обработки online/traffic
  существующим сборщиком примерно раз в минуту. Сразу после подключения
  `effective.expires_at` ещё может быть пустым; это не точное финансовое время.
- Расход имеет задержку. Для VLESS/Vision splice часть счётчика появляется
  после закрытия потока. Эти данные не являются побайтовым realtime billing.
- На patched Hysteria suspend/revoke вызывает native `/close` по auth ID;
  ошибка закрытия возвращает503, заблокированная запись остаётся для повтора.
  Legacy Hysteria suspend и изменение политики запрещают новые подключения;
  завершение уже открытых потоков не гарантируется, аналогично VLESS.
  Для обратимых операций legacy `/kick` не вызывается: Hysteria
  хранит его отметку до следующего трафика, поэтому она могла бы оборвать
  первое подключение после resume.
- При постоянном revoke Hysteria выполняет kick только при положительно
  подтверждённой online-сессии, по принципу best effort. Удалённый API-ID
  повторно не используется. Мгновенное завершение всех старых потоков
  не обещается даже при успешном ответе revoke.

## Запуск и обслуживание

API слушает `127.0.0.1:18010` от непривилегированного `vpn-control`.
Отдельный root bridge обслуживает ограниченный Unix RPC через
`/run/vpn-control-hys/bridge.sock`, проверяя peer UID и marker аккаунта.
Пароли Mongo/Marzban и глобальные настройки Hysteria не передаются боту.

Runtime credentials поступают через systemd LoadCredential. На диске хранится
каталог хешей Bearer tokens; сами выданные operator/readonly tokens сохраняются
в отдельном приватном артефакте вне Git. Публичный интерфейс или межсерверная
сеть управления не включаются этим установщиком.

ENV задаёт локальный node ID, public host, порты и SNI; параметры по умолчанию
соответствуют NL. Новый регион не требует изменения кода адаптера.
[Пример](examples/node.env.example), [операционные инструкции](deploy/OPERATIONS.md).

Зависимости закреплены в `requirements.lock`; dev/test — отдельно.
Установка использует versioned root-owned releases и переключение только
собственных units. Резервная копия локальной SQLite согласованная; восстановление
всего узла также требует резервных копий Marzban и Hysteria/Mongo.

## Проверки

Локальные тесты покрывают авторизацию/scopes, профили без утечек в БД,
повторы/конкуренцию/неопределённые результаты, сохранение идентичности,
специфику backend, ограничения тела, regional config и OpenAPI.
Живая приёмка использует только новые canary-аккаунты, старые нативные клиенты
российского стенда, lifecycle и повтор после перезапуска только нового API.
Проверки не включают списания, оплаты или изменения Telegram-бота.

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.lock
.venv/bin/python -m pytest -q tests deploy/test_backup.py
```

Снимок [OpenAPI v1](../../contracts/node-agent-v1/openapi.json) хранится вместе
с кодом для будущего адаптера Hub. Runtime `/openapi.json` требует read scope.
Приватные credentials и локальные live-квитанции не входят в Git.

На 9 ноября 2026 агент развёрнут на NL; оба backend готовы. Полный локальный
набор прошёл 94/94 теста. Финальный цикл из RU прошёл 25/25 проверок с первой
попытки: HTTPS до suspend и после resume с прежними профилями, запрет свежих
подключений после suspend/revoke, удаление собственных backend-записей,
сохранность прежних доступов и очистка стенда.
[Состав приёмки и её ограничения](acceptance/README.md).
